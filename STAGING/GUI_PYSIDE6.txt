REBUTTAL — why not stay on tkinter
  Prior suggestion: tkinter because stdlib, no wheel, stills via PhotoImage.
  That is correct for /open's little preview.
  It is incorrect for "website-parity homestead console":
    - no first-class video (need a player process anyway)
    - PDF = external or a weak canvas
    - layout of nested briefs is box-packer pain
    - one big mainloop fight with the daemon

WHY PYSIDE6 OVER THE OTHER QT BINDING
  PyQt6     GPL / commercial. Fine at home, ugly if Purposeful Strides ships.
  PySide6   official Qt for Python, LGPL. Link dynamically, ship.
  Same widgets: QLabel/QPixmap stills, QMediaPlayer + QVideoWidget clips,
                QPdfView (Qt Pdf) or QWebEngineView for HTML briefs,
                QTextBrowser for TUTORIAL.txt
  Signals/slots map cleanly onto packets + reports.
  Windows wheels exist for CPython 3.10–3.13. 3.14: verify wheel
  before you promise the TUF. If 3.14 has no wheel, venv 3.12 for GUI only.

WHY NOT ELECTRON / WEBVIEW-ONLY
  Website already exists as glass. Metal GUI should be Python talking to
  the same db/jobs as the daemon — not a second JS stack.
